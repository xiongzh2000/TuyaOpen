> 分享者：后端研发

## 一、背景（3 分钟）

- 我是谁：后端 N 年，Java/Go，熟悉分布式、服务治理
- 为什么跨端：业务需要，没有嵌入式/前端同学，只能自己上
- 结果怎样：**完成了交付**，而且比预期快很多

---

## 二、跨端的真实门槛（5 分钟）

跨端难的不是语法，是**心智模型的切换**：

| 后端思维 | 嵌入式/前端思维 |
|---------|--------------|
| 进程/线程/RPC | 中断/HAL 层/事件回调 |
| HTTP 请求响应 | 帧率/渲染树/响应式 |
| 数据库事务 | Flash KV / 内存对齐 |
| 日志看 ELK | 串口打 log，没有 IDE |

AI 的价值不只是帮你写代码，更是帮你**快速建立陌生领域的认知地图**。

## 三、实战案例：图生图打印功能（15 分钟）

### 3.1 需求背景

> 已有文生图（语音说描述 → AI 生成图片 → 热敏打印机打印）  
> 目标：支持图生图（拍照/选相册图片 + 语音指令 → AI 改图 → 打印）

### 3.2 先看底层有什么，再决定怎么做

第一步不是写代码，而是**读懂已有的管道**。

```
ai_mode_hold_vad_change()
  └── 语音 VAD 检测到说话开始
       ├── 若 ai_picture_input 队列不为空
       │    └── 先发图 → tuya_ai_image_input()
       └── 再跟上语音流 → tuya_ai_audio_input()
```

**结论**：图生图需要的底层管道已经存在，只需要打通 UI 入口和图片入队这两个环节。

> 这是后端思维的体现——**先摸清现有架构，找到可复用的接口，再决定改什么。**

### 3.3 设计决策过程

用 AI 做了一次结构化的需求澄清，逐步确认：
1. 触发方式 → 屏幕触摸按钮
2. 图片来源 → 摄像头拍照 + 相册选图
3. 语音指令输入 → 复用现有机制（长按/唤醒词），零改动

**最终改动范围极小**：

| 文件 | 改动 |
|------|------|
| `ai_ui_manage.h` | 加 2 个枚举值 |
| `lang_config.h`（JSON 源） | 加 4 个字符串 |
| `ai_ui_wechat_chat.c` | 加弹窗入口和子弹窗 |
| `app_ui_action.c` | 处理 2 个新 Action，修改 4 个已有 case |

打印链路、AI 通信层、模式状态机——**全部零改动**。

### 3.4 踩坑实录

#### 坑 1：`ENABLE_COMP_AI_VIDEO` 没生效，"拍照"按钮不显示

- 现象：弹窗里只有"从相册"，没有"拍照"
- 排查：`app_default.config` 加了 `CONFIG_ENABLE_COMP_AI_VIDEO=y`，但 `.build/cache/using.config` 仍是旧值
- 原因：`tos.py clean` 只清了 ninja 产物，**CMake 缓存没有失效**
- 修复：`rm -rf .build` 完全删除，强制 cmake 重新读取配置

> **教训**：增量构建缓存是嵌入式构建系统的常见陷阱，Kconfig 改动后要关注 `using.config` 是否真正更新。

#### 坑 2：clean 后编译报错 `IMG2IMG_READY undeclared`

- 现象：全量重建后 `lang_config.h` 里没有我们加的宏
- 原因：`lang_config.h` 是由 `gen_lang.py` 从 JSON 自动生成的，Task 1 直接改了头文件而没有改 JSON 源文件，clean 后重新生成覆盖了手改内容
- 修复：把字符串加到 `language/zh-CN/language.json`，用脚本重新生成头文件并提交

```bash
python3 scripts/gen_lang.py \
  --input language/zh-CN/language.json \
  --output include/lang_config.h
```

> **教训**：嵌入式项目中有很多"看起来是源文件、实际是生成物"的文件，改之前先确认文件头注释和 CMakeLists 的 `add_custom_command`。

### 3.5 最终效果

```
用户点 "+" → "图生图" → "拍照" 或 "从相册"
     ↓
图片保存到相册 → 加入 ai_picture_input 队列
     ↓
屏幕提示："图片已就绪，请说出编辑指令"
     ↓
用户长按按键说："把这张图改成素描风格"
     ↓
AI 收到 [图片 + 语音]，返回改图
     ↓
打印机自动打印
```

## 四、AI 协作方法论（10 分钟）

### 4.1 分层使用，不是一次性提问

```
第一层：让 AI 解释架构（"这个模块是干什么的，和哪些模块交互"）
第二层：让 AI 分析现有代码的数据流（"这个事件从哪里触发，到哪里被消费"）
第三层：让 AI 帮你写具体的改动（"在这个位置加这个逻辑"）
```

直接问"帮我实现 XXX 功能"，AI 不了解你的项目约定，生成的代码大概率要改很多。

### 4.2 把 AI 当 Code Reviewer

写完代码让 AI 做两轮 review：
1. **Spec 合规 review**：是否实现了所有需求，有没有多余的改动
2. **Code Quality review**：命名、宏保护、边界情况

> 这次发现了 `__popup_img2img_cb` 缺少 null guard，就是通过 Code Quality Review 发现的。

### 4.3 善用已有的 AI 工作流工具

- 用 **brainstorming** 梳理需求，而不是凭感觉直接写
- 用 **writing-plans** 把实现计划写清楚，让 AI 按步骤执行
- 用 **subagent-driven-development** 并行推进各子任务，每步有 review 门控

### 4.4 后端思维在跨端中的迁移

| 后端习惯 | 在跨端中的体现 |
|---------|--------------|
| 先看接口再看实现 | 先读头文件和 Kconfig，再看 .c 文件 |
| 最小改动原则 | 打通图生图只改了 4 个文件，打印链路零改动 |
| 关注分层 | 理解 TAL / Component / App 三层架构 |
| 日志定位问题 | 用 `PR_DEBUG` / 串口 log 代替断点 |

## 五、测试与调试：AI 能自动化多少？（8 分钟）

这是跨端实践里最容易被高估的环节，需要分清楚边界。

### 5.1 AI 能做的部分

**① 纯逻辑单元测试（可落地）**

TuyaOpen 支持 LINUX 目标，不依赖硬件的纯逻辑可以在本机运行。对于状态机、协议解析、数据处理这类代码，AI 可以生成有效的测试：

```c
// 例：验证 sg_img2img_pending 状态机流转
void test_img2img_pending_camera_path() {
    // 模拟 IMG2IMG_FROM_CAMERA → TAKE_PHOTO → CLOSE_CAMER
    // 验证 pending 标志在各分支下的清除是否正确
}
```

**② 生成测试用例 checklist（很实用）**

AI 帮你**穷举边界情况**，这个价值不比生成代码低。

比如问 AI："图生图功能有哪些边界情况需要验证？"，它会给出：
- 摄像头打开后直接关闭（不拍照）
- 相册选图页面直接返回（不选图）
- 图片队列已满（上限 3 张）时再次入队
- AI 只返回文字、不返回图片时
- 拍照成功但 `ai_picture_input_add_from_album` 失败时

这些边界情况，人工靠经验很容易漏掉。

**③ Code Review 发现漏测场景**

让 AI 审查你的实现，它会指出"这里没有做 null 检查"、"这个状态没有复位"——这本质上也是在帮你做测试设计。

### 5.2 AI 做不了的部分

| 场景 | 原因 |
|------|------|
| 硬件外设联调 | AI 看不到屏幕、打印机、摄像头的实际响应 |
| 实时时序问题 | I2S 帧率、中断延迟这类问题无法在软件层模拟 |
| 多设备兼容性 | 不同硬件版本的差异只有真机能暴露 |
| 最终冒烟测试 | 必须人眼看、手操设备 |

### 5.3 现实可落地的分工

```
AI 负责（能自动化）              人工负责（省不了）
────────────────────             ─────────────────
纯逻辑单元测试生成               硬件冒烟测试
测试 checklist 穷举              实时/时序问题排查
代码 review 发现漏测场景         多设备兼容验证
LINUX 目标的集成测试             最终交付验收
```

### 5.4 一个真实的感受

> AI 把我从"不懂语法"的困境解放出来，但设备上的调试、时序问题、硬件兼容性，一分都省不了。  
> **AI 节省的是 80% 的前期探索和编码成本，最后 20% 的硬件调试，只能人来做。**

这句话在分享时说出来，反而会让听众更信任你的结论——你没有过度美化 AI。

## 六、边界与反思（5 分钟）

### AI 帮不上的地方

- 硬件时序调试（示波器/逻辑分析仪）
- 特定芯片 datasheet 的细节（AI 可能给出错误信息）
- 构建系统约定（比如"这个头文件是自动生成的"这种隐含知识）

### AI 可能让你走弯路

- 生成的代码不符合项目已有规范（命名、宏保护风格）
- 不了解项目的构建约定，提出错误建议
- 过度自信——要让 AI 自我验证，不能直接采用

### 结论

> AI 是加速器，不是替代品。  
> 跨端成功的核心，还是后端的**系统思维**和**接口意识**。  
> AI 把你从"不懂语法"的困境里解放出来，让你可以专注于"把事情想清楚"。
